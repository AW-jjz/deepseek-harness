# Agent Note：录制语料声明它复现的是哪台主机

状态: implemented

[English](2026-11-01-recorded-corpus-host-boundary.md) | 中文

## 问题

录制会话这一层在 Windows 检出上几乎全红：headless 语料 174 条里 126 条失败，TypeScript SDK 的 31 个场景全败，ACP 的 8 个里败 2 个。产品侧没有任何回归。真正的原因是**两条主机环境事实被写进了录制里**，而它们在 Windows 上不同：

- 壳工具。钉住的 request header 携带主机装配出的完整工具目录，所以录制里写的是 `bash` 及其描述与参数模式，而 Windows 主机给的是 `pwsh`——描述不同、参数集不同、参数顺序也不同。
- 内置技能目录。会话会记录它启动时看到的目录行，而 Windows 多一个别的主机没有的内置技能，于是 Windows 上每个会话都比录制多一行。

在这种主机上重放，等于比较两个环境，然后把差异当成回归报出来。它还掩着第二个隐患：`test:snapshot:record` 此前**完全没有平台闸**，Windows 上的开发者本可以把 Windows 语料提交进全网重放的金标里。

## 决定

语料一次性声明它复现的主机环境，这一层在环境之外不再声称覆盖。

快照支持包里的 `recordedCorpusEnvironment` 对 `linux`/`darwin` 之外的平台返回跳过原因，并在 CI 里改为**抛错**——整层静默跳过的 lane 依然报绿，所以 CI 必须失败而不是跳过。三份语料文件把这个原因并入它们已有的逐场景跳过判断；ACP 语料由套件工厂注册，因此通过套件选项 `environmentSkipReason` 传入。每份文件打印一次原因，跳过这件事出现在运行输出里，而不是让人从计数上猜。

写回侧沿用已有的更窄规则：`test:snapshot:record` 现在和三条 refresh 脚本跑同一个平台脚本，两条写命令都在录制平台之外被拒绝。record 是更宽的写入路径，此前没有闸。

## 被否的方案

- **给每个场景标 `platform: posix`。** 先试过 31 个 SDK manifest：这个键本来就存在，语义也贴合。但作为整体方案被否——语料需要 199 个标记，而这些标记在受支持的平台上都是惰性的，新增场景还会漏标。逐场景键仍适合「可移植语料里的单个场景」。
- **在比较里归一化壳工具槽位。** 它能修好钉住的 header 差异，但技能目录那一行、录制里真正调用 `bash` 的脚本、以及工具可用性诊断都不动——于是要为每一处再补一层归一化，而每一层都是靠删掉证据来换取跑绿。
- **重新录一份 Windows 语料。** 录制是唯一诚实的 Windows 覆盖方式，代价是 199 个场景要真实 API key、提交语料翻倍，并把 Windows 夹具塞进一条要求 POSIX 的 lane 所在的仓库。
- **让失败留在原地。** 那条 lane 于 Windows 检出上会常驻 159 条无人可处理的红色断言，结果就是所有人都学会无视这条 lane 的结论。

## 后果

Windows 检出上 `pnpm run test:snapshot` 现在报 26 passed、199 skipped、0 failed，并打印每份语料的跳过原因；那 26 条是读提交夹具、不启动会话的不变量测试。`linux` 与 `darwin` 上什么都不变：判定返回无原因，所有跳过判断与从前一致。非录制平台的 CI runner 会响亮失败而不是跳过。

这条 lane 现在作出的声明窄而可核对：它在能复现语料的主机上验证语料，别处就明说。Windows 失去了那 5 个恰好能跑通的子进程场景带来的附带覆盖，ACP 失去 6 个；两者都是为了一条不会随新的平台条件能力出现而腐烂的边界所付的价。

`test:snapshot:record` 与三条 refresh 脚本现在共用同一条拒绝，于是写夹具的表面上只有一条平台规则，而不是一条有闸、一条没闸。
