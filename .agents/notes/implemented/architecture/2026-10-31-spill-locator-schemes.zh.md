# Agent Note: Spill 的定位信息按根目录之内的位置指认文件，而不是绝对路径

Status: implemented

[English](2026-10-31-spill-locator-schemes.md) | 中文

## 问题

spill 通知交给模型一串定位信息，而这串字符串会写进会话日志——也就是说，它的含义必须比写入它的进程活得更久。绝对路径能熬过一次重启，却熬不过一次搬迁：harness 主目录是用户自己的目录，便携安装换个位置、或把 `DSH_HOME` 指到别处，日志里每条定位信息就都指向一个不再存在的目录。改用相对路径也不行：`~` 展开成宿主用户的主目录，跟 harness 主目录毫无关系；相对会话工作目录的路径同样与 spill 根目录没有任何关系。

## 决定

定位信息可以按文件在某个已注册目录**之内**的位置指认它：`spill:/session-<hash>/<file>`。bundle 里两处配置、都由同一个 `dshHomePath('spill')` 表达式推导，共同支撑这件事。`spill-local` 新增 `locatorScheme`，把它写出的每条定位信息里的绝对路径替换掉，并要求显式 `root`（私有进程级临时根目录对读取方没有意义）。文件系统后端新增 `locatorRoots`，每项 `{ scheme, root }`，在**当前**配置的根目录下展开匹配的请求——`resolve` 与 `lstat` 两处都做，且位于家目录展开与相对路径锚定之前。

三条性质让这次改动是安全的，而不只是新的。两侧都是选择性开启，只设置一侧的组合仍得到今天的绝对路径，而不是打不开的句柄。绝对路径永远不会匹配某个 scheme，因此旧日志原样可用。相对部分会做包含性校验：试图爬出根目录的定位信息会被拒绝而不是被打开，因为定位信息的合法写入方只有拥有该目录的那个后端。

搜索工具在启动 ripgrep 之前解析同一个 scheme。定位信息不是真实路径，而 `grep`/`glob` 会把目标交给子进程，原样传递会让「建议搜索 spill 结果」这条取回指引失效。

## 考虑过的替代方案

**保留绝对路径并记录该限制。** 成本最低，也是根目录稳定之后的现状：重启安全，但搬迁不安全。这种失败是静默且滞后的——模型几周后读到一条过期定位信息，只会报告文件不存在——所以当根目录本身已可配置时，这个残余值得关掉。

**把根目录写进定位信息，读取时改写过期前缀。** 这要求读取方去猜路径里哪一段是可搬动的部分，而且无法区分「根目录搬走了」与「根目录被删了」。scheme 是显式声明契约，而不是靠推断。

**给文件系统 seam 增加定位信息解析器——抽象方法或新服务。** 两者都会把新的词汇与新的生命周期塞进 `ctx.fs`，而那是每个后端和每个组合都要实现的接口。在已经各自拥有契约一半的两个包上各加一个配置项，不新增服务、不新增事件、不新增抽象方法，因此不会破坏任何第三方。

**只在工具层为 `read` 做解析。** 这样会漏掉 `lstat`、`edit` 以及未来所有消费方，而且把知识放进了消费方，而不是拥有路径解析的后端。

## 后果

主目录搬迁后，scheme 上线之后写入的每条定位信息都继续可用。搬迁前已写成绝对路径、且根目录随后被搬走的定位信息，用这里的任何改动都追不回来——关于其根目录的信息本就不在那串字符串里。

两侧必须同步：scheme 名与目录在配置里各写一次，`packages/bundle/base/tests/base.spec.ts` 钉住两行携带同一个表达式。设置了 `locatorScheme` 却没有匹配的 `locatorRoots` 条目，就会产出读取方自己打不开的定位信息——这也是该选项默认不设、而非自动推断的原因。

home 锚定之前的 `%TEMP%\dsh-spill-*` 根目录不属于本契约；它们的定位信息是绝对路径，由既有的发现与清扫逻辑处理，而不是由 scheme 处理。
