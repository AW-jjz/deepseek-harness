# Agent Note: Token 计价读脚本构成，而不是只看长度

Status: implemented

[English](2026-10-31-cjk-aware-token-density.md) | 中文

## 问题

固定启发式规则把每四个字符算作一个 token，而它数的是 UTF-16 单元，于是一句中文的真实价格约为每字一 token，却被测成四分之一。每回合有两处机制读这个数字：压缩决定何时折叠上下文，spill 策略决定哪条工具结果大到不能内联。两者在 CJK 内容上都因此晚了四倍才触发——失败表现为提供方拒绝一个超长请求，而那时会话已经按错的价格写完了。

这条缺陷在 v8.2 台账里对中文用户是 P0 级的噪声（P1-30）：`CHARS_PER_TOKEN = 4` 与 `maxInlineTokens: 12500` 都未改，而包 README 自己的限制章节就写着「CJK 文本与 JSON schema 在每 token 四字符下严重低估」。

## 决定

计价改为遍历一次文本并按码点分类：ASCII 保持每 token 四字符的密度，其余每个码点记一整个 token。拉丁文本因此与改前逐字同价，而中日韩等宽字符脚本回到每字约一 token——这正是真实 tokenizer 给它们的量级。

分类集中在一个导出函数 `estimateTextTokens` 里，启发式的每个文本分支都调用它：text 与 reasoning 块、工具调用的名字与参数、系统提示词，以及结构块与工具 schema 的 `JSON.stringify` 路径。保持单一实现，才是维持「计量服务与上下文拆分投影把同一内容算成同一个数」这条既有契约的前提。

高估是安全的方向。猜高的启发式会提前压缩、提前 spill；猜低的启发式要等到提供方那里才发现错。

## 考虑过的替代方案

**按提供方的精确分词器。** 长期正确答案，也是源码地图仍称其为启发式的原因。它需要每个路由一套分词器实现与词表，而本包目前除类型外没有依赖；除非词表随日志一起固定并版本化，否则还会改变回放稳定性。在提供方能给出可信的 token 计数之前，不值得打包进来。

**给宽字符脚本一个固定比率，例如 1.5 字符/token。** 对散文更接近某些 tokenizer，对标识符、标点与混合代码则是错的。按码点计价不需要标定，也不会低于 ASCII 分支。

**把密度做成配置项。** 外部没人能设对：取值取决于内容的脚本构成，那是计量看得到、运维看不到的东西。

## 后果

中文密集的会话现在会更早压缩、更早把大工具结果 spill 出去，这是有意的交换：预算花在请求失败之前，而不是之后。

带重音的拉丁文、西里尔文、希腊文与符号密集文本现在会高估，最多达四倍；emoji 无论提供方怎么切分都按每字符一 token 计。这是保守方向上的可接受高估，包 README 的限制章节已如实写明。

录制测试语料里没有任何数字被重新计价：token-meter、压缩、spill 与 tool-web 各套夹具全是 ASCII，所以这次改动对它们是数值上不可见的——能抓住漂移的守卫，是新加的 `tests/estimate.spec.ts` 用例与逐文件覆盖率闸。
